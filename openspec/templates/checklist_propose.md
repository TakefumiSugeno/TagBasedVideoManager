# Proposeレビュープロトコル（挑戦的設問型）

対象: `proposal.md` / `specs/**/spec.md` / `design.md` / `test_plan.md` / `tasks.md` / `mockup.html`（Proposeフェーズ計画成果物）
レビュアー: User Reviewer Agent & SE Reviewer Agent

> [!IMPORTANT]
> 単なる追認・同語反復を排し、以下の各成果物に特化した**挑戦的設問（悪魔の代弁者・ブラインド比較・故障シミュレーション）**に具体的に回答してください。
> すべての設問に具体的な確認根拠（ファイル名・行番号・シナリオ名等）を記載し、`reviews.md` に追記してください。

---

## 1. 仕様書（`specs/**/spec.md`）のブラインド比較レビュー

**担当: User Reviewer Agent**

1. **異常系・境界条件の先出し突合**:
   - `specs/` を読む前に、`proposal.md` の背景と目的（Why/What）だけを読み、この機能を実装する上で**考慮から漏れやすいエッジケース・異常系・境界条件をゼロベースで5点予測**してください。
   - その後、実際の `specs/` を開き、あなたの予測のうち仕様書に書かれていない項目・未定義の振る舞いを指摘してください。
2. **都合の良い前提（暗黙の仮定）の告発**:
   - 仕様書が「ユーザーは正しく操作する」「通信は成功する」といった都合の良い前提に依存している箇所はないか？

## 2. 設計書（`design.md`）の故障シミュレーション

**担当: SE Reviewer Agent**

1. **外部依存ハング・切断時の連鎖崩壊検証**:
   - この設計における最大の外部依存（API・DB・ファイル・プロセス・通信）が**「5秒間ハング」または「処理途中で切断」**された時の挙動をシミュレートしてください。
   - システムが安全にリカバリできず、状態の不整合、リソースリーク、またはリトライ無限ループを起こす設計上の穴を1箇所特定してください。
2. **可観測性（調査可能性）の検証**:
   - 本番で障害が発生した時、エラーログやメトリクスを見ただけで根本原因が1分で特定できる設計になっているか？ 診断情報が足りない箇所を指摘してください。

## 3. テスト計画書（`test_plan.md`）の死角告発

**担当: SE Reviewer Agent（または QA Reviewer）**

1. **100%パスしても抜けるバグ（最大の死角）**:
   - このテスト計画に定義されたテストが全件100% Passしたとしても、**本番環境ですり抜けてしまう可能性が最も高いバグパターン（未検証の領域）トップ2**を挙げてください。
2. **モックの嘘（偽の安心感）の検証**:
   - 外部I/Oをモック（スタブ）にしすぎた結果、「モックの挙動をテストしているだけで、本番の挙動を何も保証していないテスト」になっている箇所はないか？

## 4. UIモック（`mockup.html`）の初心者ペルソナ検証（UI変更時のみ）

**担当: User Reviewer Agent（UI/UX変更を伴わない場合は「対象外」と記載可）**

1. **Zero-State（初期状態）の手抜き告発**:
   - データが1件もない時、または初回起動時に、画面が真っ白になったり何をすればよいか途方に暮れる設計になっていないか？
2. **Error-State（エラー時）の回復導線**:
   - 処理失敗時に、赤文字で「エラーが発生しました」とだけ表示して放置されていないか？ ユーザーが再試行・設定修正できる具体的な回復導線が提示されているか？

## 5. タスクリスト（`tasks.md`）の手戻りリスク検証

**担当: SE Reviewer Agent**

1. **最も詰まるリスクが高いタスクの特定**:
   - このタスクリストの中で、作業途中で仕様の未確定事項や依存関係の逆転にぶつかって中断（ブロック）するリスクが最も高いタスクはどれか？
2. **完了基準の検証可能性**:
   - タスクの完了基準が曖昧で、「どこまで作れば完了と言えるか」作業者が迷うタスクを指摘してください。

## 総合判定

- **LGTM**: true / false（`Critical` または `Major` 指摘がある場合は必ず `false`）
- **条件付きLGTM**: <条件がある場合記載>
- **指摘サマリ**:
  - `Critical`: <件数> 件（致命的な設計破綻・仕様不整合）
  - `Major`: <件数> 件（重大なエッジケース漏れ・障害リスク）
  - `Minor`: <件数> 件（軽微な改善点）
  - `Suggestion`: <件数> 件（将来の拡張・リファクタ候補）
- **承認者**: <レビュアーロール名>
