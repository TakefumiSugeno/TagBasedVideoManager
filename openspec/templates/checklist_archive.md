# Archive総括レビュープロトコル（技術的負債自白・初見エンジニア型）

対象: 変更全体の成果物（実装・テスト・仕様・ドキュメント・申し送り事項・ゲート検証結果）
レビュアー: 全役割（User / SE / PG / QA Reviewer Agent）

> [!IMPORTANT]
> DoD（テスト全件Pass、skip放置ゼロ、ビルド・静的解析エラーゼロ、フォーマット差分ゼロ）は `verify-gate.ps1 -Gate archive` が機械的に判定します。
> レビュアーは言葉による優等生的な追認を排し、以下の**「隠された技術的負債の自白」**および**「初見エンジニア視点の問答」**に具体的に回答してください。

---

## 1. 隠された技術的負債・妥協点の自白（悪魔の代弁者）

**担当: SE Reviewer Agent ＆ PG Reviewer Agent**

今回の変更において、工数や手間の都合で「本当は直したかったが見て見ぬふりをした妥協点や時限爆弾」を自白してください。

1. **今回あえて残した技術的負債**:
   - 今回の実装で、急ぎのGreen化やスコープ制限のために「後でリファクタが必要」と分かっていながら放置した箇所はあるか？
   - その負債は `handover.md` の「技術的負債・申し送り事項」に具体的に記録されているか？
2. **将来の機能追加で踏み抜く可能性が高い罠**:
   - 次にこのモジュールに新しい機能を追加しようとするエンジニアが、知らずに壊してしまいそうな暗黙の前提や結合箇所はどこか？

## 2. 初見エンジニア視点でのドキュメント検証（Whyの欠落告発）

**担当: User Reviewer Agent**

明日からこのリポジトリを一人で引き継ぐ初見の新人エンジニアの視点で検証してください。

1. **設計の背景（Why）の追跡可能性**:
   - 変更されたコード、README、仕様書、および `handover.md` を読んだだけで、「なぜこの設計・この実装にしたのか（ボツ案・トレードオフ）」が理解できるか？
   - コードを読まないと分からないような暗黙の前提や、Whyが欠落している箇所を指摘せよ。
2. **トラブルシューティング手順の十分性**:
   - もし本番でこの機能が不正動作した時、運用者が即座に原因特定・切り分け・ログ確認できる手順がドキュメント化されているか？

## 3. ロールバック・安全性の最終検証

**担当: SE Reviewer Agent ＆ QA Reviewer Agent**

1. **ロールバック（Revert）手順の検証**:
   - 万が一このPRのマージ後に致命的な不具合が発覚した場合、`git revert` または設定変更だけで安全に直前の安定状態へ巻き戻せるか？
   - データベース変更や外部設定変更がある場合、後戻り不能な破壊的変更が含まれていないか？
2. **保留指摘の全件引き継ぎ確認**:
   - Applyフェーズで「保留（Minor/Suggestion）」とした全指摘が、漏れなく `handover.md` の「将来の改善候補」に転記されているか？

---

## 総合判定

- **LGTM**: true / false（隠された負債が未記録である場合、またはロールバック不能な場合は必ず `false`）
- **条件付きLGTM**: <条件がある場合記載>
- **引き継ぎ完了確認**: handover.md に全ての負債・申し送りが記録済み
- **リリース可否**: 即時リリース可 / 要注意 / リリース不可
- **承認者**: User / SE / PG / QA Reviewer Agent
