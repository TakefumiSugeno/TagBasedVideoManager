# Design: Webアプリケーション仕様のOpenSpec移行 (migrate-web-specs)

## Context

本プロジェクトは、バックエンド（F# Giraffe + SQLite + FFmpeg）とフロントエンド（HTML5 + Alpine.js + Tailwind CSS）からなるWeb動画管理システムと、長パス対策デスクトップコンパニオン（F# Avalonia.FuncUI）の2つのサブシステムで構成されている。
デスクトップコンパニオン側はすでに OpenSpec（`companion-file-rename`, `companion-docker-control`）で厳密に仕様管理されているが、Webアプリ本体の仕様は旧ドキュメント（`doc/spec.md`, `doc/design_detail.md`）にのみ存在し、リポジトリ全体としての仕様管理が非対称な状態であった。
また、コードベースと旧仕様書の突合により、サムネイル配信（静的ファイル配信）やタグ解除APIなどで実装との乖離が確認された。

## Goals / Non-Goals

### Goals

- Webアプリケーション本体の仕様を、ユーザーの機能価値を軸にした5大モジュール（`video-library`, `video-scanner`, `tag-management`, `search-and-folders`, `viewing-analytics`）に体系化し、OpenSpecのメイン仕様へ移行する。
- 既存の実装コード（真実）に基づき、旧ドキュメントとの乖離を是正した正確な契約（Requirement / Scenario）を定義する。
- 仕様書と既存テストスイート（xUnit Unit/Integration, Playwright E2E）のトレーサビリティを確立する。
- レビューで指摘されたエッジケース（循環参照、ファイル未存在、Zero-State）および技術的負債を可視化する。

### Non-Goals

- 本Changeにおけるプロダクションコード（F# ソースコード、フロントエンドHTML/JS）の機能追加・破壊的改変
- UIデザインやレイアウトの変更（UI変更を伴わないため `mockup.html` の作成は対象外）
- 旧 `doc/` ディレクトリの強制削除（過去の経緯資産として保持しつつ、仕様の正本を `openspec/specs/` に一本化）

## Decisions

### 1. ユーザーの「機能価値」を軸とした5大ドメイン分割

- **決定**: 内部ソースファイル単位（`Scanner.fs`, `Media.fs` 等）ではなく、ユーザーが利用する機能価値（`video-library`, `video-scanner`, `tag-management`, `search-and-folders`, `viewing-analytics`）で仕様モジュールを分割した。
- **理由**:
  - ユーザーやレビュアーにとって「何の価値を提供する仕様か」が直感的に理解しやすい。
  - 将来の機能追加時（例: お気に入り機能拡張）に、UI・API・DBが1つの仕様書内で完結し、複数仕様書をまたぐ断片化を防げる。
- **代替案（不採用）**:
  - _内部F#ファイル単位（6〜7分割）_: 実装構造に引きずられ、リファクタリング時に仕様の境界が壊れやすくなるため見送り。
  - _巨大な単一仕様書（1分割）_: コンテキストが肥大化し、OpenSpecのデルタ仕様としての更新が困難になるため見送り。

### 2. コード実態（真実）に基づく仕様定義

- **決定**: 旧ドキュメント（`doc/spec.md`）の誤りや古い記述ではなく、稼働しているコードベースを正（Truth）として仕様書に反映した。
  - サムネイル取得: `GET /api/videos/{id}/thumbnail` ではなく、静的ファイルプロバイダーによる `/thumbnails/{id}.jpg` 配信として明文化。
  - タグ解除: `DELETE /api/videos/{id}/tags/{tagId}` ではなく、`DELETE /api/videos/{id}/tags` に JSON body `{ "tagId": "..." }` を送信する仕様として明文化。
  - ヘルスチェック: `GET /api/ping`（"pong" 応答）を仕様に正式追加。
- **理由**: 仕様駆動開発において、実態と乖離した仕様書を作成するとテストの失敗や将来の改修時の誤認を招くため。

### 3. ブラックボックス（観測可能な振る舞い）による要件・シナリオ記述

- **決定**: 仕様書の Requirement および Scenario には内部クラス名・関数名・内部変数を一切含めず、「ユーザーの操作」「API入出力契約」「DB永続化状態」「UI描画挙動」のみを明文化した。
- **理由**: 実装のリファクタリング（関数分割やモジュール再構成）を行っても仕様書が壊れず、E2Eテストや受け入れテストの検証基準として恒久的に機能させるため。

## Risks / Technical Debt (技術的負債と運用リスク)

本Changeは既存コードの実態に基づく仕様移行であるが、SE Reviewerの故障シミュレーションにより以下の重要な技術的負債が特定された。これらは将来の機能改善Change（`feat` / `fix`）にて対処すべき既知の負債として管理する。

1. **[FFmpeg外部プロセスハング時のキュー凍結リスク]**
   - **現状**: `Media.fs` でのプロセス実行にタイムアウトが設定されておらず、破損動画等でFFmpegが無応答になるとセマフォ（キャパシティ1）が永久ブロックされ、後続のメディア処理が完全停止する。
   - **当面の緩和策**: `POST /api/media/stop` による手動強制終了APIを常備。
   - **将来の改善方針**: プロセス実行ヘルパーへのタイムアウト（例: 30秒）および自動 `Kill`・スキップ機構の導入。
2. **[再起動によるエラーログ自動消滅とコンテキスト欠落]**
   - **現状**: `DbInit` において `DELETE FROM ErrorLogs;` が実行されるため、障害発生時の再起動で直前のエラーログが消滅する。またログに動画IDやファイルパス等の引数が含まれない。
   - **当面の緩和策**: Dockerの標準出力ログ（Kestrelコンソール）と併用して調査。
   - **将来の改善方針**: 起動時クリアから件数保持・ローテーション削除への変更、およびログレコードへの操作コンテキスト（VideoId, FilePath）の追加。
3. **[過去ドキュメント参照による開発者の混乱]**
   - **現状**: 旧 `doc/spec.md` が残存するため、古いエンドポイントを参照してしまう恐れがある。
   - **緩和策**: `doc/spec.md` の冒頭に「本ドキュメントは過去の初期仕様であり、現在の正本は `openspec/specs/` 配下に移行済みである」旨の案内注記を追加する。

## Migration Plan

1. 本Change（`migrate-web-specs`）の Propose レビュー（`user-reviewer` / `se-reviewer`）を実施し、合意を形成する。
2. Apply フェーズにおいて、既存テストとの対応付けを確認し、`doc/spec.md` に移行注記を追記する。
3. 仕様デルタをメイン仕様（`openspec/specs/`）へマージ・同期（Archive）する。
