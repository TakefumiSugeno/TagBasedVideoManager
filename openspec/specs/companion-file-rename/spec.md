# companion-file-rename Specification

## Purpose

ホストOS上の指定動画フォルダを再帰走査し、Dockerバインドマウントの制限（260文字）に抵触する長パスファイル（設定値初期値: 240文字以上、起動中一時変更可）を自動検出した上で、設定された命名規則とOpenRouterのFreeモデルを活用して短縮新ファイル名および問題発生時のAIコメントを提案し、安全に物理リネームおよびUndo（元に戻す）を行う機能を提供する。

## Requirements

### Requirement: マウント不可（パス長超過）ファイルの自動抽出と起動中閾値変更

システムは、指定されたルートディレクトリ配下の動画ファイル（.mp4等）を再帰的にスキャンし、Windows パス長制限（フルパス文字数 ≧ 閾値、初期値: 240文字）または Linux ファイル名制限（ファイル名単体の UTF-8 バイト数 ≧ 閾値、初期値: 240バイト）のいずれか一方にでも抵触するファイルを自動抽出して一覧表示しなければならない（SHALL）。また、ユーザーは起動中にUI上でこの抽出基準文字数・バイト数を一時変更できなければならないが、設定ファイルへは書き戻してはならない（SHALL NOT）。

#### Scenario: 初期値による自動抽出と起動中の一時閾値変更

- **WHEN** ユーザーが「リネーム対象抽出＆AI提案を実行」を実行したとき
- **THEN** 設定ファイルの初期値（240文字または240バイト）以上のファイルが抽出され、UI上で数値を変更した場合は設定ファイルを更新することなく即座に対象ファイル一覧が動的に絞り込まれること

#### Scenario: Windows長パスファイルとLinux長ファイル名ファイルの包括抽出

- **WHEN** 指定フォルダ内にフルパス105文字だがファイル名UTF-8バイト数270Bのファイル、およびフルパス250文字でファイル名UTF-8バイト数90Bのファイルが存在し、スキャンを実行した時
- **THEN** 両方のファイルが漏れなく抽出結果一覧に含まれる

#### Scenario: 両方の基準を満たす安全なファイルの除外

- **WHEN** フルパス120文字かつファイル名UTF-8バイト数150Bの安全な動画ファイルが存在し、スキャンを実行した時
- **THEN** そのファイルは抽出結果一覧に含まれない

### Requirement: 命名規則マネージャー（作成・編集・削除・並び替え・永続化）

システムは、命名規則の作成・編集・削除・優先順位並び替えが可能な管理モーダルを提供し、設定（`companion-settings.json`）のリスト先頭にあるルールを起動時の既定値として適用しなければならない（SHALL）。

#### Scenario: 命名規則の並び替えと既定ルール適用

- **WHEN** ユーザーが管理画面でルールを一番上に移動して保存したとき
- **THEN** 次回起動時にそのルールが自動選択され、AIプロンプト生成の既定として適用されること

### Requirement: OpenRouter Freeモデルによる新ファイル名および問題発生時AIコメントの提案

システムは、抽出されたファイル情報および選択された命名規則プロンプト（Web検索結果を含む）をOpenRouterのモデルに送信し、文字数上限および Linux の UTF-8 バイト数上限（拡張子を含め UTF-8 で 240 バイト以内、かつフルパス 240 文字以内）を満たす新ファイル名候補を取得しなければならない（SHALL）。また、正常時・例外時を問わず、命名の意図・根拠・短縮内容（またはWeb検索結果の反映内容）を説明する「AIコメント」を必ず生成・保持し、常時表示しなければならない（SHALL）。

#### Scenario: 風変わりなファイル名に対するAIコメント表示

- **WHEN** 元のファイル名がランダムな英数字列等で命名規則に完全に従うことが困難なファイルに対しAI提案を生成したとき
- **THEN** 正常に命名できたファイルも含め、補完・例外理由や短縮根拠を説明するAIコメントが生成され、常時表示されること

#### Scenario: 通常短縮時およびWeb検索補完時のAIコメント常時表示

- **WHEN** ユーザーが抽出されたファイルに対してAI提案を実行したとき
- **THEN** 正常に命名できたファイルも含め、すべての提案ファイルに対して命名根拠・短縮理由を説明するAIコメントが生成され、常時表示されること

#### Scenario: UTF-8バイト数とフルパス文字数の両立短縮プロンプト送信

- **WHEN** 抽出された候補ファイル群に対してAI提案を開始した時
- **THEN** システムはプロンプトに「新ファイル名は拡張子を含めてUTF-8で240バイト以内とし、変更後のフルパスが240文字以内に収まるようにすること」を指示に含めてOpenRouterへリクエストを送信する

#### Scenario: AI提案成功時の両制約遵守とAIコメント生成

- **WHEN** OpenRouterから正常な新ファイル名候補と理由が返却された時
- **THEN** 各候補の新ファイル名が設定され、短縮意図を説明するAIコメントが保持・表示される

### Requirement: Before / After 対比プレビュー表示（上下並び・左右並び切り替え）

システムは、変更前（Before）と変更後（After）、およびAIコメントを対比表示するUIを提供しなければならない（SHALL）。各ファイル候補カードにおいて、「旧ファイル名 (BEFORE)」「新ファイル名 (AFTER)」「AIコメント (AI COMMENT)」の3行を常時固定表示し、文字数に加えてファイル名単体の UTF-8 バイト数を常時併記しなければならない（SHALL）。上下並び表示において、BEFORE行とAFTER行の左側ラベル領域の幅をコンパクトに固定（195px等）し、ファイル名テキストおよび入力欄の開始X座標を左に寄せて垂直に完全に一致させなければならない（SHALL）。また、AFTER においてフルパス文字数が閾値未満かつファイル名 UTF-8 バイト数が 240 バイト以内である場合に「✓ [安全]」バッジを表示し、241〜255 バイトの場合は注意バッジ（黄色）、256 バイト以上またはフルパスが閾値以上の場合は該当する危険警告バッジ（赤色）を表示しなければならない（SHALL）。

#### Scenario: 上下並びでの素早い目視確認と手動修正

- **WHEN** 上下並び表示モードを選択したとき
- **THEN** 各ファイルのBefore行とAfter行、および常時表示されるAIコメント行が最小限の高さで隣接して描画され、ユーザーが新ファイル名を直接テキストボックスで手動微調整できること

#### Scenario: 3行常時表示による素早い目視確認と手動修正

- **WHEN** 候補一覧を表示したとき
- **THEN** 各候補カード内に「BEFORE行」「AFTER行」「AI COMMENT行」の3行が常に描画され、未提案状態ではプレースホルダー、提案完了後は新ファイル名とAIコメントが整然と表示されること

#### Scenario: 両制約クリア時の安全バッジ表示

- **WHEN** AFTERの新ファイル名がフルパス180文字かつファイル名UTF-8バイト数160Bである時
- **THEN** AFTER行に「AFTER (180字 / 160B [安全])」バッジが緑色（安全色）で表示される

#### Scenario: 手動編集によるLinuxバイト数超過時の即時警告表示

- **WHEN** ユーザーがAFTERの新ファイル名を手動編集し、ファイル名UTF-8バイト数が256バイト以上となった時
- **THEN** AFTER行のバッジが「AFTER (〇〇字 / 〇〇B [Linux危険])」の赤色警告バッジに即座に切り替わる

### Requirement: 重複回避と安全な物理リネーム実行

システムは、ユーザーが確定した新ファイル名へのリネームを実行する際、移動先ファイル名の重複チェックを行い、同名ファイルが既に存在する場合は末尾に連番サフィックス（`_1.mp4`等）を付与して一意なファイル名を導出しなければならない（SHALL）。連番付与時においても、最終ファイル名が UTF-8 で 240 バイト以内およびフルパス 240 文字以内を維持するよう必要に応じてベース名をトリミングし、上限を再超過させてはならない（SHALL NOT）。エラー時は安全にロールバックして結果レポートを表示しなければならない（SHALL）。

#### Scenario: 一括リネームの安全な実行

- **WHEN** ユーザーがチェックしたファイルに対して一括リネームを実行したとき
- **THEN** ホストOS上で物理ファイルがリネームされ、成功・失敗（および失敗理由）が画面上に明確にレポートされること

#### Scenario: 同名衝突時の連番サフィックス付加とバイト数再超過防止

- **WHEN** リネーム先のディレクトリに同名ファイルが既に存在し、連番サフィックスが付加された時
- **THEN** サフィックス付加後のファイル名が UTF-8 で 240 バイト以内およびフルパス 240 文字以内に維持された状態で安全に移動が行われること

### Requirement: アプリ起動中リネームの Undo（元に戻す）実行

システムは、アプリ起動中に実行されたリネームの変更履歴（旧パスと新パスの対応）を保持し、ユーザーが「元に戻す」を実行した際に物理ファイルを元の名前に復元し、コンテナを再起動しなければならない（SHALL）。

#### Scenario: 直前のリネームの取り消し

- **WHEN** ユーザーが「直前のリネームを元に戻す」ボタンをクリックしたとき
- **THEN** リネームされた全ファイルが元のファイル名に逆リネームされ、Dockerコンテナが再起動されて以前の状態に戻ること

### Requirement: シンボリックリンクおよびジャンクション（リパースポイント）の追跡と安全走査

システムは、指定された走査対象フォルダ配下に存在するシンボリックリンクやディレクトリジャンクションを解釈・追跡し、その配下の動画ファイルを抽出対象に含めなければならない（SHALL）。また、同一ディレクトリへの再訪や循環参照（サイクル）を検知し、無限ループに陥ることなく安全にスキップしなければならない（SHALL）。

#### Scenario: ディレクトリジャンクション配下の動画ファイル走査

- **WHEN** 走査対象フォルダ配下に別のボリュームやディレクトリを指すジャンクションが存在するとき
- **THEN** ジャンクション配下の動画ファイルも再帰的に走査・抽出され、循環参照が存在しても安全に走査が完了すること

### Requirement: 画面要素のテキスト選択・コピー機能

システムは、走査対象フォルダパス、各ファイルのフォルダパス、変更前ファイル名などの主要なテキスト情報を、ユーザーがマウス操作で選択・クリップボードにコピー可能（Selectable）にしなければならない（SHALL）。

#### Scenario: 抽出されたパス情報のコピー

- **WHEN** ユーザーが抽出結果カード内のフォルダパスやファイル名をマウスドラッグで選択したとき
- **THEN** テキストが選択状態となり、標準のショートカット（Ctrl+C 等）でクリップボードへコピーできること

### Requirement: 抽出結果一覧のソート順指定

システムは、抽出されたファイル一覧に対しソート機能を提供しなければならない（SHALL）。既定ソートは危険度の高い「パス長 (降順)」とし、UI上で「元ファイル名 (昇順/降順)」「更新日時 (新しい順/古い順)」等に切り替え可能でなければならない（SHALL）。

#### Scenario: ソート順の変更

- **WHEN** ユーザーがツールバーでソート順を「元ファイル名 (昇順)」に切り替えたとき
- **THEN** 抽出候補カードが元ファイル名のアルファベット・五十音順で即座に並び替えられること

### Requirement: Before / After 対比プレビューの視覚的整列と等幅比較

システムは、上下並び表示においてBEFORE行とAFTER行の左側ラベル幅を固定し、ファイル名の開始X座標を垂直に完全に一致させなければならない（SHALL）。また、BEFORE行とAFTER行の高さを同一に揃え、ファイル名の比較・編集欄には同一の等幅フォント（monospace）を適用しなければならない（SHALL）。短縮文字数バッジ内の数字と文字のベースライン・上下位置を整えて表示しなければならない（SHALL）。

#### Scenario: 上下並びでのファイル名比較と整列

- **WHEN** 上下並び表示モードで候補カードを表示したとき
- **THEN** BEFORE行とAFTER行のファイル名開始位置が垂直に揃い、同一の等幅フォントおよび行高さで整然と描画され、短縮文字数バッジ内の文字と数字がガタつきなく整列して表示されること

### Requirement: 参照ボタンによるフォルダ選択ピッカー連携

システムは、対象フォルダ入力欄の「参照...」ボタンをクリックした際に、OS標準のフォルダ選択ダイアログ（`StorageProvider`）を表示し、ユーザーが選択したディレクトリパスを即座に対象フォルダ欄に反映しなければならない（SHALL）。

#### Scenario: フォルダピッカーによる走査対象ディレクトリの指定

- **WHEN** ユーザーが「参照...」ボタンをクリックしてフォルダを選択したとき
- **THEN** 選択されたフォルダのフルパスが対象フォルダ入力欄に自動設定されること

### Requirement: 命名規則マネージャーモーダルのUI表示と操作

システムは、「⚙ 管理...」（または「⚙ 命名規則」）ボタンをクリックした際に命名規則管理モーダルを表示し、登録された命名規則の一覧表示、新規作成、既存ルールの編集、削除、および上下並び替え（先頭ルールが既定）を行えなければならない（SHALL）。
モーダルダイアログは、左右2ペイン構成（左ペイン: ルール一覧、右ペイン: ルール詳細・編集フォーム）とし、十分な視認性と作業スペースを確保するため広域サイズ（幅 960px、高さ 680px）で描画しなければならない（SHALL）。
システムは、既存ルールの優先度並び替え（「▲」「▼」）および削除（「🗑」）に加え、**既存ルールの内容編集（「✏️ 編集」）を提供しなければならない（SHALL）。**
**ルール一覧において「🗑」削除ボタンが押下された場合、即座にルールを削除してはならず（SHALL NOT）、削除対象のルール名を表示した確認ダイアログ（「命名規則『〇〇』を削除しますか？」）を表示し、ユーザーが「削除する」を選択したときのみ削除を実行しなければならない（SHALL）。**
また、ルール編集・新規作成フォームにおけるプロンプト指示文の入力エリアは、縦領域を活かした複数行テキストエリアとし、長文の指示文を見渡して編集できるようにしなければならない（SHALL）。
ルール内の「Pattern」フィールドは、ファイル抽出フィルタではなくAIに対するファイル名形式指示であることを明確化するため、UI上では「命名パターン (テンプレート):」と表記し、ファイル名本体のみを対象とするため拡張子を含めない形式として、プレースホルダーに `{Code}_{Summary}_{Actor}` 等の命名フォーマット例を提示しなければならない（SHALL）。

#### Scenario: 命名規則マネージャーモーダルの開閉と操作

- **WHEN** ユーザーが「⚙ 管理...」ボタンをクリックしたとき
- **THEN** 画面前面に命名規則マネージャーモーダルがオーバーレイ表示され、ルールの追加・編集・削除・順序変更および「閉じる」操作が行えること

#### Scenario: 既存ルールの選択と編集・上書き保存

- **WHEN** ルール一覧で既存ルールの「✏️ 編集」ボタンをクリックしたとき
- **THEN** 右ペインの編集フォームにそのルールの情報（ルール名、命名パターン、Web検索有効フラグ、プロンプト指示文）が読み込まれ、編集モード（「✏️ ルール編集中: 〇〇」）となること
- **WHEN** 編集フォームで内容を変更し「💾 この内容で保存」をクリックしたとき
- **THEN** ルール一覧内の該当ルールが同一の順序位置を保ったまま上書き更新され、設定ファイル（`appsettings.json`）に永続化されること

#### Scenario: ルール編集のキャンセル

- **WHEN** ルール編集モード中に「✕ 編集をキャンセル」ボタンをクリックしたとき
- **THEN** 編集中の変更が破棄され、新規ルール作成モード（空の入力フォーム）に戻ること

#### Scenario: 新規ルールの追加

- **WHEN** 左ペイン下部の「➕ 新規ルールを作成」ボタンをクリックし、右ペインでルール名およびプロンプトを入力して「💾 この内容で保存」をクリックしたとき
- **THEN** 新しいルールが一覧の末尾に追加され、設定ファイルに永続化されること

#### Scenario: ルール削除時の確認ダイアログ表示と安全削除

- **WHEN** ルール一覧の「🗑」ボタンをクリックしたとき
- **THEN** 即時削除されず、「命名規則『〇〇』を削除しますか？」という確認ダイアログが表示されること
- **WHEN** 確認ダイアログで「削除する」をクリックしたとき
- **THEN** 対象ルールが削除されて一覧および設定ファイルが更新され、ダイアログが閉じること
- **WHEN** 確認ダイアログで「キャンセル」をクリックしたとき
- **THEN** ルールは削除されず、ダイアログのみが閉じること

#### Scenario: 左右2ペインレイアウトと広域プロンプトテキストエリア

- **WHEN** 命名規則マネージャーモーダルを開いたとき
- **THEN** モーダルが幅960px・高さ680pxで展開され、左ペインにスクロール可能なルール一覧、右ペインに広域な編集フォームが表示され、プロンプト指示文のテキストエリアが複数行を一覧できる十分な高さを確保して表示されること

### Requirement: 長ファイル名表示時の親コンテナ幅維持と外枠完全描画

システムは、ウィンドウ幅を超える長大なファイル名（240文字以上）や長いAIコメント、長いディレクトリパスを表示する際、候補カード全体の青い外枠（Border）が親コンテナ幅（ウィンドウ幅）を超えて画面外へはみ出さないよう、全行で横幅クリッピングおよび親ScrollViewerの水平スクロール抑止を適用し、外枠の右端・下端が常に画面内に完全に閉じて描画されなければならない（SHALL）。また、短縮文字数バッジ（`-〇〇字 (〇〇%短縮)`）内の数字と日本語文字の上下ズレ・ベースラインの浮き沈みを排除するため、日本語と欧文のメトリクスが揃ったフォント（`Yu Gothic UI`, `Segoe UI`, sans-serif）を適用して高さを完全に一致させなければならない（SHALL）。

#### Scenario: 長大ファイル名表示時の外枠完全描画とバッジ高さ揃え

- **WHEN** 長大なファイル名および短縮バッジを上下並びカードで表示したとき
- **THEN** カードの青い外枠（Border）の右端が切れることなく完全に閉じて描画され、短縮バッジ内の数字と「字」「短縮」の文字が上下にズレることなく同一ベースライン・高さで整然と描画されること

### Requirement: .NET標準外部設定ファイル（appsettings.json / appsettings.{Environment}.json）からの設定取得と環境別ファイルへの保存

### Requirement: 新ファイル名 (AFTER) 行の緑色背景と文字数抵触時の部分警告表示

システムは、新ファイル名（AFTER）行を緑色（エメラルド基調）をベースとして描画しなければならない（SHALL）。新ファイル名のフルパス文字数が現在の抽出基準文字数（閾値）以上である場合（文字数抵触時）、AFTER行の左端ラベルバッジ「AFTER (〇〇字 [危険])」の背景色のみを赤色（危険色）に変更して明示的に警告しなければならない（SHALL）。基準文字数未満（安全）である場合は、同ラベルバッジを緑色（安全色）で「AFTER (〇〇字 [安全])」と表示しなければならない（SHALL）。

#### Scenario: 文字数抵触時におけるAFTERラベルバッジの赤色警告表示

- **WHEN** 提案された（または手動編集された）新ファイル名のパス文字数が抽出基準文字数（閾値）以上であるとき
- **THEN** AFTER行の全体は緑色基調を保ちつつ、左側の「AFTER (〇〇字 [危険])」ラベルバッジの背景色のみが赤色で強調表示されること

#### Scenario: 安全文字数達成時におけるAFTERラベルバッジの緑色表示

- **WHEN** 新ファイル名のパス文字数が抽出基準文字数未満となったとき
- **THEN** 左側の「AFTER (〇〇字 [安全])」ラベルバッジの背景色が緑色で表示され、安全であることが明確に視認できること

### Requirement: AI提案中におけるリネーム実行ボタンの非活性化（誤リネーム防止）

システムは、スキャン直後の即時IO描画後およびAI提案パイプラインの処理中（`IsRequestingAi = true`）において、「リネームのみ実行」および「リネームしてコンテナ再起動」ボタンを非活性（Disabled）とし、ユーザーによる未提案状態の誤リネームを防止しなければならない（SHALL）。全ファイルのAI提案処理が完了した段階でのみ、選択された候補数が1件以上存在する場合にリネーム実行ボタンを活性化（Enabled）しなければならない（SHALL）。また、AI提案処理中はフッターに進捗状況（「AI提案中... (〇/〇件完了)」）を明示しなければならない（SHALL）。

#### Scenario: AI提案中のボタン非活性化と完了後の活性化

- **WHEN** 「リネーム対象抽出＆AI提案を実行」を実行し、AI提案が処理中であるとき
- **THEN** リネーム実行ボタン群は非活性（クリック不可）となり、フッターに完了件数進捗が表示され、全件の提案が完了した時点でリネーム実行ボタンが活性化されること

### Requirement: AI提案中における処理の中止および新条件での再実行

システムは、ツールバーに「AI提案を中止」ボタンを常時配置しなければならない（SHALL）。中止ボタンはAI提案パイプラインの処理中（`IsRequestingAi = true`）のみ活性化（Enabled）され、非処理時は非活性（Disabled）としてレイアウトのガタつきを防止しなければならない（SHALL）。中止操作が行われた場合、実行中のWeb検索サブプロセスおよびLLMリクエストを安全にキャンセル（CancellationToken）し、処理を中断して待機状態に戻らなければならない（SHALL）。また、AI提案の処理中であっても、ユーザーが走査フォルダ、閾値、命名規則等の条件を変更して「リネーム対象抽出＆AI提案を実行」をクリックした場合、システムは実行中の前処理を直ちにキャンセルした上で、新しい条件で安全に再抽出およびAI提案を開始しなければならない（SHALL）。

#### Scenario: AI提案の中止操作

- **WHEN** AI提案パイプラインが実行されている途中でユーザーが「中止」をクリックしたとき
- **THEN** 実行中の非同期処理が直ちにキャンセルされ、未完了行のアニメーションが解除されて待機状態に戻ること

#### Scenario: AI提案中における新条件での再実行

- **WHEN** AI提案パイプラインが実行されている途中でユーザーが条件を変更して「抽出＆AI提案を実行」をクリックしたとき
- **THEN** 進行中だった前回の処理が安全にキャンセルされ、新しい条件で直ちにファイル再抽出およびAI提案が最初から開始されること

### Requirement: ファイル名に日本語を含まない動画の抽出オプション

システムは、動画ファイル走査時、ファイル名本体（拡張子を除くベース名）に日本語文字（ひらがな、カタカナ、CJK統合漢字）を含まないファイルのみを抽出対象とするフィルタオプションを提供しなければならない（SHALL）。
本オプションはGUIツールバー上のチェックボックス（「ファイル名に日本語を含まないもののみ抽出」）により有効・無効を切り替え可能とし、起動時の初期状態は無効（OFF）としなければならない（SHALL）。
本オプションが有効な場合、システムは「フルパス文字数 ≧ 抽出基準（閾値）」かつ「ファイル名本体に日本語文字が1文字も含まれない」ファイルのみを候補として抽出しなければならない（SHALL）。
本オプションが無効な場合は、ファイル名に含まれる言語文字にかかわらず、「フルパス文字数 ≧ 抽出基準（閾値）」の動画ファイルを抽出対象としなければならない（SHALL）。

#### Scenario: 日本語を含まないフィルタ有効時の抽出

- **WHEN** 「ファイル名に日本語を含まないもののみ抽出」オプションを有効にして走査を実行したとき
- **THEN** パス長が閾値以上かつファイル名本体にひらがな・カタカナ・漢字が1文字も含まれない動画ファイルのみが抽出され、ファイル名に日本語文字を1文字でも含む動画ファイルは候補一覧から除外されること

#### Scenario: 日本語を含まないフィルタ無効時の通常抽出

- **WHEN** 「ファイル名に日本語を含まないもののみ抽出」オプションを無効にして走査を実行したとき
- **THEN** ファイル名本体の言語文字にかかわらず、パス長が閾値以上のすべての動画ファイルが候補一覧に抽出されること

#### Scenario: 閾値0と組み合わせた全件抽出

- **WHEN** 抽出基準（閾値）を0に設定し、「ファイル名に日本語を含まないもののみ抽出」オプションを有効にして走査を実行したとき
- **THEN** パス長に関係なく、ファイル名本体に日本語を含まないすべての動画ファイルが候補一覧に抽出されること

#### Scenario: フォルダ名に日本語が含まれる場合の判定独立性

- **WHEN** 親ディレクトリなどのフォルダパスに日本語が含まれているが、ファイル名本体には日本語が含まれていない動画ファイルを走査したとき
- **THEN** フォルダパスの日本語に影響されることなく、ファイル名本体の判定のみに基づいて正しく抽出対象として扱われること

### Requirement: 対比確認リスト最下部の完全スクロール表示と末尾余白

システムは、Before/After対比確認リスト（`ScrollViewer`）において、マウスホイールまたはスクロールバーで最下部までスクロールした際に、最後の候補カード全体（BEFORE行、AFTER行、AI COMMENT枠、およびカード外枠）が完全に視認可能となるよう、十分な下部余白（スクロールマージン／パディング）を確保しなければならない（SHALL）。リスト最下部の要素がウィンドウ境界線やフッターバーに隠れて見切れてはならない（SHALL NOT）。

#### Scenario: 最下部スクロール時の末尾カードおよびAIコメント枠の完全表示

- **WHEN** 候補一覧を最下部までスクロールしたとき
- **THEN** リスト内の最後の候補カードの下端、AI COMMENT枠、およびカード外枠の全体が完全に画面内に表示され、その下に快適な余白（約30px以上）が存在すること

### Requirement: 環境別設定ファイル（appsettings.Development.json / appsettings.Production.json）のGit管理完全除外

システムは、ローカル環境固有のディレクトリパスや API キーを格納する環境別実ファイル（`appsettings.Development.json` および `appsettings.Production.json`）を `.gitignore`（`**/appsettings.Development.json`, `**/appsettings.Production.json`）へ登録し、Web・デスクトップ両プロジェクトにおいて Git バージョン管理対象から完全に除外しなければならない（SHALL）。また、`.env` や `.env.sample` への依存ファイルはリポジトリに保持してはならない（SHALL NOT）。

#### Scenario: appsettings.Development.json / appsettings.Production.json の Git 非追跡

- **WHEN** Web または Renamer ディレクトリに `appsettings.Development.json` または `appsettings.Production.json` を作成・編集したとき
- **THEN** 両ファイルとも Git の追跡対象・未追跡差分（`git status`）に現れず、リポジトリに誤コミットされないこと

#### Scenario: 既存追跡環境ファイルおよび .env.sample のリポジトリ除外確認

- **WHEN** `git ls-files` で追跡中ファイルを検査したとき
- **THEN** `.env.sample`、`appsettings.Development.json`、および `appsettings.Production.json` のいずれも Git インデックスに登録されていないこと

### Requirement: 制約違反理由の可視化と表示フィルタ

システムは、抽出された各ファイルに対し、どの制約に違反しているか（Windows パス長超過、Linux ファイル名超過、または両方超過）を判定し、候補カードの BEFORE 行に専用バッジ（`[🪟 Windows: パス長超過]`、`[🐧 Linux: ファイル名超過]`、`[⚠️ 両方超過]`）を表示しなければならない（SHALL）。また、ツールバーに表示フィルタを提供し、「すべて」「Linuxファイル名超過のみ」「Windowsパス長超過のみ」「両方超過」の条件でリストを絞り込み表示できなければならない（SHALL）。さらに、抽出候補が 0 件の時やフィルタ適用で該当ファイルが 0 件となった場合、リスト領域に全件安全である旨を示す Empty State メッセージを表示しなければならない（SHALL）。

#### Scenario: 制約種別バッジの正確な表示

- **WHEN** フルパス100文字・ファイル名UTF-8バイト数270Bのファイルが表示された時
- **THEN** BEFORE行に「🐧 [Linux: ファイル名超過 (270B / 上限255B)]」の赤色バッジが表示される

#### Scenario: 表示フィルタによるLinux超過ファイルの絞り込み

- **WHEN** ユーザーが表示フィルタで「Linuxファイル名超過のみ」を選択した時
- **THEN** ファイル名UTF-8バイト数が閾値（240バイト）以上のファイルのみがリストに表示され、Windowsパス長のみが超過しているファイルは一時的に非表示となる

#### Scenario: 表示フィルタを「すべて」に戻した際の全件再表示

- **WHEN** 表示フィルタを「すべて」に切り替えた時
- **THEN** 抽出されたすべての候補ファイルが再び一覧に表示される

#### Scenario: 候補0件時のEmpty State案内表示

- **WHEN** 走査対象ディレクトリ内に制限超過ファイルが1件も存在しない、またはフィルタ条件に合致する候補が0件である時
- **THEN** リスト領域に「対象ファイルはありません。すべてのファイルが安全です」の安心メッセージが表示される

### Requirement: アクティブ構成環境および保存先ファイル名のGUI明示表示

システムは、AI File Renamer のメイン画面（ヘッダーまたはフッター領域）に、現在適用されている実行環境名（例: `DEV` / `PROD`）および設定保存先の環境別ファイル名（例: `appsettings.Development.json` / `appsettings.Production.json`）を視認性の高いバッジとして表示しなければならない（SHALL）。

#### Scenario: 画面上のアクティブ環境バッジ表示

- **WHEN** AI File Renamer を `Development` または `Production` 環境で起動したとき
- **THEN** メイン画面上に現在の環境名バッジと保存先ファイル名（`appsettings.Development.json` または `appsettings.Production.json`）が表示されること

### Requirement: スキャン・AI提案・リネーム/Undo実行中のローディングスピナーUIと確実な解除および回復導線

システムは、AI File Renamer におけるすべての非同期・時間のかかる処理および Zero-State / Error-State において、Fluent Dark テーマと調和する回転スピナーアニメーションおよび適切な回復導線を表示し、処理完了・キャンセル・エラー終了時にはスピナーを確実に解除して次の状態へ遷移させなければならない（SHALL）。

1. **初回・フォルダ未設定時の Zero-State ガイダンス**: `TargetDirectory` が未設定（空文字）である場合は、誤ってスキャンを実行して即エラーとならないよう、一覧領域にフォルダ選択を促す Zero-State ガイダンス（「対象フォルダが未設定です。上の『📁 参照...』からフォルダを選択してください」）を表示しなければならない（SHALL）。
2. **フォルダスキャン中 (`IsScanning = true`)**: 候補一覧領域に未実行プレースホルダーや Empty State を表示してはならず（SHALL NOT）、中央に回転スピナーおよび「動画ファイルをスキャン中...」メッセージを表示しなければならない（SHALL）。また、スキャン完了後の 0 件判定時は「フォルダ内に動画が 0 本であった」場合と「動画を 1 本以上検査し制限超過ファイルが 0 件であった（安全）」場合を明確に出し分けなければならない（SHALL）。
3. **AI 提案処理中 (`IsRequestingAi = true` / `c.IsAiProcessing = true`) および個別失敗回復**: フッターの進捗バッジ（「AI提案中... (x/y件完了)」）および処理中の各候補カード（`c.IsAiProcessing = true`）に回転スピナーをインライン表示しなければならない（SHALL）。また、特定ファイルの AI 提案が HTTP エラー・レート制限・タイムアウト等で個別失敗した場合は、該当カードのみ赤枠エラー状態（失敗理由および「↻ この項目を再試行」ボタン付き）として表示し、他ファイルの処理・結果を維持したまま個別再試行できなければならない（SHALL）。
4. **リネーム・Undo 実行中 (`IsRenaming = true`)**: 候補一覧領域上に半透明の操作ブロックオーバーレイと中央スピナー（「ファイル名を変更中...」または「変更を元に戻しています...」）を表示し、処理完了またはエラー発生までカード編集・条件変更・再実行を防止しなければならない（SHALL）。
5. **スキャン・リネーム中の入力排他およびエラー時確実解除**: `IsScanning = true` または `IsRenaming = true` の間はディレクトリ・閾値・ルール・モデルの変更入力を受け付けず状態整合性を保護しなければならない（SHALL）。走査エラー、AI 提案キャンセル／タイムアウト、リネーム失敗時は、いずれのビジーフラグも `false` に戻してスピナーを解除し、ユーザーが原因を確認して設定変更・再試行を行えるエラーメッセージを表示しなければならない（SHALL）。

#### Scenario: 対象フォルダ未設定時の Zero-State ガイダンス表示

- **WHEN** `TargetDirectory` が空のクリーン設定状態で AI File Renamer を起動したとき
- **THEN** 一覧領域にフォルダ未設定の案内メッセージとフォルダ選択を促す表示が現れ、未設定のまま誤ってスキャンが実行されないこと

#### Scenario: ディレクトリスキャン中のスピナー表示と Empty State 抑止・0件出し分け

- **WHEN** ユーザーが有効なディレクトリを指定して「⚡ 抽出 ＆ AI提案を実行」をクリックし、`IsScanning = true` となったとき
- **THEN** 一覧領域に未実行案内や Empty State は表示されず、中央に回転スピナーと「動画ファイルをスキャン中...」が表示されること
- **WHEN** スキャンが完了し対象候補が 0 件であったとき
- **THEN** フォルダ内に動画ファイル自体が 0 本の場合と、1 本以上を検査して全件安全基準内であった場合とでメッセージが明確に出し分けられること

#### Scenario: AI 提案処理中の行インラインスピナーおよび個別カード失敗・再試行

- **WHEN** スキャンが完了し、候補ファイルに対して非同期 AI 提案が実行されているとき（`IsRequestingAi = true`）
- **THEN** 処理中の候補カード上に回転スピナー付きで「検索・AI提案中...」が表示され、フッターにも回転スピナー付きの完了件数進捗バッジが表示されること
- **WHEN** 特定の候補カードで API エラーやタイムアウトにより AI 提案が個別失敗したとき
- **THEN** 該当カードのスピナーが解除されて失敗理由と「↻ 再試行」ボタンがカード内に表示され、他候補の成功結果は維持されたまま個別再試行できること

#### Scenario: リネームおよび Undo 実行中の操作ブロックオーバーレイスピナー表示

- **WHEN** ユーザーがリネーム実行または Undo を実行し `IsRenaming = true` となったとき
- **THEN** 候補一覧領域に半透明オーバーレイと中央スピナーが表示され、完了後にスピナーが解除されて最新リストへ遷移すること

#### Scenario: 非同期処理エラー・キャンセル時のスピナー確実解除と入力排他維持

- **WHEN** フォルダ不在エラー、API エラー、または「⏹ 中止」ボタンによるキャンセルが発生したとき
- **THEN** すべてのスピナーが即座に解除され（`IsScanning = false`, `IsRequestingAi = false`, `IsRenaming = false`）、操作ボタンが回復してエラー通知または再開可能な待機状態に戻ること
